# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An implementation of the design in [agent-sync-dev-spec.md](agent-sync-dev-spec.md) — a CRDT-based synchronization layer that lets multiple coding agents edit the same repository concurrently without lost writes, plus presence awareness and (later) cross-file dependency-change awareness. **That spec is the source of truth for design decisions, terminology, and build order** — read it before making architectural changes, and keep it in sync if a change here implies the spec is wrong or out of date (as has happened already in this project's history).

Build order follows the spec's Section 10 phases exactly. Do not build a later phase's mechanism (transparent tool interception, disk flush, validation gate, symbol index, locks) ahead of schedule — each phase is sequenced to de-risk the next. Check the spec's phase list before assuming a subsystem doesn't exist yet vs. hasn't been reached yet.

Whenever a change lands in this repo (a new phase, a bug fix, a behavior change to an existing mechanism), add an entry to [CHANGELOG.md](CHANGELOG.md) describing what changed and why — grouped under the relevant phase (or a phase addendum, as with the Bash-bypass fix), not by date. Do this in the same turn as the change, not as a separate follow-up.

## Architecture

### Wire protocol (`src/protocol/messageTypes.ts`)

Messages are framed with a one-byte outer envelope — `MESSAGE_SYNC = 0`, `MESSAGE_AWARENESS = 1`, or `MESSAGE_LOCK = 2` (Phase 6) — written with `lib0/encoding`. Inside a sync envelope is a `y-protocols/sync` sub-message (its own type byte: sync-step-1, sync-step-2, or update); inside an awareness envelope is a `y-protocols/awareness`-encoded update, itself wrapped as a `varUint8Array` field (`encoding.writeVarUint8Array` / `decoding.readVarUint8Array`) rather than raw bytes — get this wrapping wrong and decoding silently misaligns. A lock envelope wraps a JSON-encoded `LockRequestPayload`/`LockResponsePayload` (`src/protocol/lockMessages.ts`) via `writeVarString`/`readVarString` — no y-protocols encoder involved, since there's no existing library for a small request/response lease protocol the way there is for CRDT/awareness. This two-layer (now three-type) framing means a future channel can be added without changing how existing message types are parsed — do not collapse the layers; `MESSAGE_LOCK` is the example of that actually happening.

Do not hand-roll CRDT or presence logic anywhere — `yjs` + `y-protocols/sync` + `y-protocols/awareness` own all merge/encoding/staleness logic; this codebase only wires transport (WebSocket, reconnect) around them. When behavior seems like it needs a workaround, check how the reference `y-websocket` implementation handles it first (see the two gotchas below, both resolved that way) rather than inventing protocol-level cleverness.

### Sync server (`src/server/syncServer.ts`)

One `Y.Doc` **and** one `Awareness` instance per "room," keyed by the WebSocket connection's URL path (`ws://host:port/<docName>`). The server has no concept of what a doc name means (file path, arbitrary key, etc.) for merge purposes — that mapping is entirely a client-side concern for the CRDT/awareness logic in this file. (`DiskFlushService`, from outside this class, does treat a doc name as a relative file path when it flushes — see the Disk flush section below — but `SyncServer` itself stays agnostic.) Rooms are created lazily on first connection and, once created, live for the lifetime of the server process — they are *not* torn down when the last client disconnects, only when `SyncServer.close()` runs (which also destroys each room's `Awareness`, or its internal heartbeat `setInterval` leaks across tests). Even with Phase 4's disk flush in place, an in-memory room is still the only copy of anything not yet flushed, so "keep the room alive with no clients connected" still matters.

`SyncServer` extends `Observable<string>` (same base class `SyncClient` and `Awareness` use) and emits a `docUpdate` event — `{ docName, content }` — on every local `Y.Doc` update, plus `getDocNames()`/`getDocContent(docName)` to read current state without opening a `SyncClient`. This is Phase 4's hook: `DiskFlushService` listens to `docUpdate` rather than connecting its own client, since the server already holds the canonical in-memory content in the same process.

The constructor takes an optional `SyncServerOptions.hydrate: (docName) => string | undefined` (Phase 4 addendum). `getRoom` calls it exactly once per room, at creation, synchronously and *before* attaching the `doc.on("update")` handler and before the first client is greeted — so a connecting client's sync-step-1/2 exchange already carries the seeded content, and no `docUpdate` fires for it. Seeded content is announced with a separate `docHydrated` event (`{ docName, content }`) instead. The server still has no idea what a doc name means — `createDiskHydrator` (see Disk flush below) is what treats it as a path, from outside this class, the same way `DiskFlushService` does.

`setValidationRejection(docName, message)`/`clearValidationRejection(docName)` (Phase 5) write/clear a `rejection` entry in a reserved `_validation` Y.Map on the *same* `Y.Doc` as the file's `content` Y.Text — deliberately not a side channel or a new wire-protocol message. Mutating it fires the same `doc.on("update")` handler as any content edit, so it rides the existing CRDT sync broadcast to every connected client for that doc automatically. See the Disk flush section below for why the doc name is still just a string to this class either way.

On every local `Y.Doc` update, the server rebroadcasts the encoded update to every *other* client in that room (`origin` is the originating `WebSocket`, used to avoid echoing a client's own update back to it). Awareness updates, by contrast, are rebroadcast to *every* client including the origin — that's not a bug, it's what the reference implementation does too, since the awareness clock check makes the echo a harmless no-op.

The `Awareness` constructor gives its owning doc a phantom local state (`{}`), as if the room itself were a peer. The server clears this immediately (`awareness.setLocalState(null)`) so the room never shows up as a fake connected agent.

A per-connection `Set<number>` tracks which awareness clientIDs a given WebSocket introduced, so that on disconnect the server can `removeAwarenessStates` for exactly those IDs (a client's Y.Doc `clientID` isn't necessarily 1:1 with its WebSocket connection in general, so this bookkeeping — copied from `y-websocket`'s reference server — is what makes cleanup correct rather than approximate).

`SyncServer` accepts port `0` to get an OS-assigned port; use the `.port` getter to read back the actual bound port (used by tests to run multiple server instances in parallel without port collisions).

Each room also holds at most one lock lease (Phase 6, spec Section 4/12) — see the Lock service section below for why this lives here (server-arbitrated) rather than riding the Y.Doc/awareness channels the way Phase 5's rejection notice does.

**Construction changed in Phase 7**: the constructor now builds an explicit `node:http` `Server` and hands it to `WebSocketServer` as `{ server }`, instead of letting `WebSocketServer({ port })` create and own a standalone server internally. This is what makes `GET /status` (see the Dashboard section below) possible on the same port as the WS upgrade traffic — a consequence is that `close()` must close `httpServer` itself (`wss.close()` alone no longer tears down the listening socket, since `wss` doesn't own it) and the `.port` getter now reads `httpServer.address()` rather than `wss.address()`.

### Client (`src/client/SyncClient.ts`)

Wraps a `Y.Doc` and an `Awareness` instance, mirrors the server's sync/awareness handshakes, and reconnects with jittered exponential backoff on an unintended disconnect (`autoReconnect`/`reconnect` options). Two non-obvious protocol details, both hit and fixed during development — check here before re-deriving them from scratch if a symptom like these resurfaces:

1. **`whenSynced()` must key off the sync sub-message type, not "any sync message received."** `readSyncMessage()` from `y-protocols/sync` returns which sub-message it just processed; only a `messageYjsSyncStep2` reply actually carries document content. The very first message after connecting is typically the *server's* sync-step-1 greeting (its state vector, not data) — treating that as "synced" resolves the promise before the real content-bearing reply arrives.
2. **Re-asserting presence after a reconnect must go through `setLocalState()`, never a raw re-encode of the existing state.** When the server drops a *remote* client's awareness entry (`removeAwarenessStates` on disconnect), it deletes the state but does **not** bump that client's clock — only a *local* removal bumps its own clock. So a client that re-sends its old, unchanged state after reconnecting would carry the same clock as before, and the receiving side's staleness check (`currClock < clock`) silently drops it as a no-op. Calling `setLocalState(getLocalState())` forces the clock forward (mirrors `Awareness`'s own internal heartbeat-renewal code) and is what actually gets picked up on the other end.

Like the server, the client clears its own phantom `{}` local awareness state on construction — an agent that hasn't called `setPresence()` shouldn't appear as a contentless peer to everyone else.

`SyncClient` is the transport + CRDT/presence plumbing that Phase 3's tool-interception mechanisms sit on top of — it has no idea an MCP proxy or FUSE mount exists above it.

`simulateNetworkDrop()` is a test-only hook (hard `.terminate()`, no close handshake, doesn't set the intentional-close flag) used to exercise reconnect without a real network — it's how `test/reconnect.test.ts` triggers a drop.

### Tool interception (Phase 3, spec Section 3)

Two genuinely different interception mechanisms, per Section 3.0 — both funnel into one shared normalized layer rather than talking to Yjs directly:

**`src/sync/syncFileOps.ts` — `SyncFileOps`.** The `editFile`/`readFile` normalization point Sections 3.1/3.2/3.3a all describe: one `SyncClient` per file path (lazily connected, cached), exposing `readFile`, `writeFileFull` (blind full-buffer write), `writeFileFromSnapshot` (full-buffer write with an honest before/after), and `writeFileRange` (explicit `old_str`/`new_str`). Neither the MCP proxy nor the FUSE driver touches a `Y.Doc` or `SyncClient` directly — everything routes through here, so a third interception mechanism (direct tool-registry rebinding, Section 3.3) would reuse the exact same class.

**`src/sync/textMerge.ts` — the merge algorithms, kept as pure functions independent of `SyncFileOps` so they're unit-testable without a server:**
- `applyContentDiff(ytext, newContent)` — char-level diff of `newContent` against `ytext`'s *live* content, applied as minimal insert/delete ops instead of clear-and-reinsert. Used when there's no record of what the writer last saw (blind `full_replace`), so a concurrent edit inside the replaced range can still be lost — there's no way to tell "writer meant to delete this" from "someone else changed it since".
- `computeMinimalReplacement(oldSnapshot, newContent)` — turns a writer's own honest before/after into a minimal `{oldStr, newStr}` pair (common prefix/suffix trimmed to a small context margin). This is what lets the FUSE write path (which has a real snapshot from `open()`) go through the *same exact-match-or-reject discipline as an explicit `range_replace` call* per spec Section 3.3a, rather than needing separate merge logic — **do not replace this with a fuzzy/approximate matcher** (a `diff-match-patch`-style approach was tried and reverted: it silently overwrote a concurrently-edited span instead of rejecting, which directly violates Section 3.2's "never fuzzy-match, only exact-match-or-reject" rule stated for `range_replace` — the same rule the spec explicitly says applies to FUSE writes too).

**`src/mcp/` — the generic MCP proxy (Section 3.2).** `McpSyncProxy` (`proxy.ts`) is an MCP server (facing the agent) that also holds an MCP client (facing the real upstream server): `tools/list` is forwarded verbatim so the agent can't tell a proxy exists; a `tools/call` is diverted to `SyncFileOps` only if its tool name matches an entry in the mapping config, otherwise passed through untouched. `mappingConfig.ts` parses/validates `.agent-sync-mcp-map.yml` (example at `examples/agent-sync-mcp-map.example.yml`) — deliberately strict: an unrecognized `op`, a `write` mapping with no `mode`, or `range_replace` with no `range_params` is a config-load error, never a guessed default (Section 3.2's "ambiguous/composite tools need an explicit mapping" rule). `presets.ts` ships the generic-filesystem-server shape and a Claude-Code-native-tool-names shape as copy-pasteable starting points (Section 3.4). Errors come back as `isError: true` with the actionable message text (Sections 3.5/3.6) — MCP's own conventional tool-failure shape, not a novel one.

**`src/fuse/` — the virtual filesystem driver (Section 3.3a).** `SyncFsOperations` (`syncFsOperations.ts`) holds the real logic — a per-fd in-memory buffer populated from `SyncFileOps.readFile` on `open()`, mutated by `read`/`write`/`truncate`, and only pushed to the sync layer via `writeFileFromSnapshot` on `flush`/`release` (mirrors how a real filesystem driver buffers between open and close). This is exercised directly by `test/fuseSync.test.ts` with no real OS mount involved — it's plain async/sync methods, transport-agnostic. `mountSyncFs.ts` is the actual `fuse-native` binding on top of it, mapping a `RangeMismatchError` (a rejected merge) to `EAGAIN` and everything else to `EIO`, per Section 3.6's error-code table. **This file cannot be exercised in this environment**: mounting needs macFUSE's kernel extension enabled via System Settings on macOS (libfuse on Linux, WinFsp on Windows) — none of that is installed here, and enabling it is a system-security change left to whoever runs this for real, not something this codebase does for you. If a symptom shows up only in a real mount and not in `fuseSync.test.ts`, suspect the `fuse-native` binding layer in `mountSyncFs.ts`, not `SyncFsOperations`.

### Disk flush + git commit (Phase 4, spec Section 6)

Two pieces, deliberately kept separate from everything above them:

**`src/sync/lineEndings.ts` — `toLf`/`fromLf`.** "LF canonical internally; convert on flush" (spec Section 6) means normalization happens in *two different places for two different reasons*, not one: `toLf` runs inside `SyncFileOps` at every write entry point (`writeFileFull`, `writeFileFromSnapshot`, `writeFileRange`), so the CRDT itself never holds anything but LF regardless of which interception mechanism or which agent's editor produced the write — this is what keeps two agents with different EOL settings from generating a whole-file textual diff purely from that. `fromLf` runs only in `DiskFlushService`, at the moment content is written to disk, converting to whatever style that instance is configured with. Don't add line-ending handling anywhere else — a third normalization point is how these silently disagree with each other.

**`src/flush/diskFlushService.ts` — `DiskFlushService`.** Debounces per-doc (`debounceMs`, default 3000ms per Section 6's suggested 2–5s range — tunable, since it directly trades commit noise against how long a broken intermediate merge can sit unflushed before anything catches it), then writes the doc's current content to `<repoRoot>/<docName>` and does a commit-per-flush (`git add` + `git commit`, via `simple-git`). No validation gate yet (that's Phase 5) — every flush commits unconditionally; a `git commit` on an unchanged tree (e.g. re-flushing after a restart) is treated as success, not an error. `flushPath(docName)` flushes one doc immediately and cancels its pending timer; `flushAll()` is the manual/CLI-style flush across every currently active doc. Constructed with an explicit `repoRoot` + options today — reading `flush.debounce_ms`/`line_endings` out of `.agent-sync.yml` is Phase 7 (the file doesn't exist yet).

`src/server/index.ts` wires this in only when `AGENT_SYNC_REPO_ROOT` is set (so the standalone server binary still has zero persistence by default, matching every earlier phase) — this env-var wiring is a stopgap for exercising Phase 4 by hand before Phase 7's config file exists, not the intended long-term interface.

**`src/flush/diskHydration.ts` — `createDiskHydrator(repoRoot)`, the other direction.** Returns the `hydrate` callback `SyncServer` calls on room creation (see the Sync server section): reads `<repoRoot>/<docName>` from the working tree if it's a regular file, or returns `undefined` (room starts empty, as before) for a missing file, a directory, or a doc name that would escape `repoRoot` — the same refuse-to-escape discipline as `DiskFlushService.resolveWithinRepo`. It lives next to `DiskFlushService` because it shares that "doc name is a path under the repo root" convention, and `startAgentSyncServer` installs it whenever a `repoRoot` is configured, so both server entry points get it with no new flag. It applies `toLf` on the way in — that is not a third line-ending policy contradicting the "two normalization points" rule above: it's a write *entry point into the CRDT*, exactly like `SyncFileOps`'s write methods, and the invariant that the CRDT never holds anything but LF has to hold for content arriving from disk too. Disk-side style still lives only in `DiskFlushService`'s `fromLf`. `DiskFlushService` listens to `docHydrated` and primes both `lastSeenContent` and `lastFlushedContent` with the seeded text, so hydrated content — already on disk by definition — is neither re-written nor no-op-committed by the first `docUpdate` or by a manual `flushAll()`. Hydration is once-per-room: a later disk change made behind the server's back is not re-read, because after creation the room is the source of truth, not disk. This retired the hook bridge's disk-seeding heuristic (see that section below).

### Validation gate (Phase 5, spec Section 6)

**`src/validation/validationGateService.ts` — `ValidationGateService`.** Deliberately knows nothing about git, flushing, or the sync layer — `run()` just executes the configured shell `command` in `cwd` and reports `{ passed, output }` (combined stdout+stderr). This is what makes it unit-testable with a plain `node -e "..."` command and reusable outside a flush later (e.g. a CLI `agent-sync validate`). `onFail` (`"reject_merge"` | `"warn_only"`) lives on this class but the *decision* of what to do with a failure is `DiskFlushService`'s job, not this one's.

**`DiskFlushService` integration.** Per spec Section 6, the git commit boundary moved to "after a successful flush **and** a passing validation gate": `doFlush` now writes to disk, then (if `validation` was passed to the constructor) runs it *before* `git add`/`git commit`:
- **Pass** → commit as before (Phase 4 behavior when no `validation` is configured at all).
- **Fail + `reject_merge`** → the on-disk write is reverted (`git checkout HEAD -- <path>`, or `rm` if this would have been the file's first-ever commit) and the commit is skipped entirely — "revert the flush," per spec. The CRDT itself is **not** touched — the live `Y.Doc` still holds the merged-but-failing content, so agents keep editing against current reality (Section 6: "leave pre-flush state active so agents can retry against current reality") rather than a version silently reset out from under them.
- **Fail + `warn_only`** → commits anyway, but emits a `validationWarning` event (`{ docName, command, output }`) so the failure isn't silent. Early-development-only per the spec; not meant for production configs.
- A `reject_merge` failure also calls `server.setValidationRejection(docName, message)` with the spec's exact recommended EVALIDATE template text (Section 3.6) and emits `validationRejected` (`{ docName, command, output }`).

**Surfacing the rejection back through the agent's tool-error path (Section 3.5/3.6).** Flush is debounced and decoupled from any single tool call, so there's no in-flight request to attach the failure to — instead, `SyncFileOps`'s three write methods (`writeFileFull`/`writeFileFromSnapshot`/`writeFileRange`) each start by consuming (reading-then-deleting) the doc's `_validation`/`rejection` Y.Map entry; if one is present they throw `ValidationRejectedError` (`code: "EVALIDATE"`) instead of applying the write. Consumed **once**: the delete is itself an ordinary CRDT op that converges everywhere, so the *next* write after the rejected one proceeds normally against current content — this is what makes "re-read the current file state before retrying" (the message text) actually true rather than a dead end. `hasPendingRejection(path)` is a non-consuming peek used by `test/validationGate.test.ts` to wait out the server→client propagation delay before asserting a throw, rather than racing it. `readFile` never checks this — Section 3.6's rejection message is specifically about writes, so a plain read should keep returning current content unconditionally.

Because the rejection notice rides the same `Y.Doc` as file content, `DiskFlushService`'s own `docUpdate` handler had to stop treating *every* doc update as "content changed, schedule a flush" — it now tracks `lastSeenContent` per doc and only schedules when the flushed *text* actually differs from what it last saw, so writing the rejection notice (a Y.Map mutation, not a Y.Text one) doesn't re-trigger the exact flush-and-fail cycle that produced it. `test/validationGate.test.ts`'s "does not re-trigger auto-flush" test is what would catch a regression here.

**`toErrorResult` in `src/mcp/proxy.ts`** checks for a `.code` string property on the thrown error rather than an `instanceof` per error class — `RangeMismatchError`'s `EAGAIN` and `ValidationRejectedError`'s `EVALIDATE` both flow through the same branch, and a future coded rejection type needs no change there. `mountSyncFs.ts`'s FUSE error mapping has no POSIX equivalent for `EVALIDATE`, so it falls into the existing generic-`EIO` branch — per Section 3.6, only the message text needs to carry the actionable instruction in that case, not the code.

**Concurrent flushes across different docs are now serialized** (`DiskFlushService`'s internal `queue`, a promise chain every `flushPath` call — timer-driven or manual — is threaded through regardless of doc name). This was a latent, mostly-harmless race in Phase 4 (two docs' debounce timers firing close together could run two `git commit`s back to back fast enough to rarely collide); Phase 5 makes it a real one, since a slow validation command widens the window between "write to disk" and "commit" enormously. `test/validationGate.test.ts`'s serialization test proves two docs' validation runs don't overlap in time.

### Lock service (Phase 6, spec Section 2/4/12)

**Why this one isn't done the Phase 5 way.** Phase 5's validation-rejection notice rides the same `Y.Doc` as file content (a Y.Map entry) because it only needs to converge *eventually* to one consistent value — a race between two writers there just means the notice briefly looks different to different peers before Yjs's deterministic merge settles it, which is harmless for a one-shot notice. A lock is different: spec Section 2 calls for `"CRDT-based merge, not locks, for the default path"` and locks as the deliberate exception "for declared hot files only" — the whole point is to *avoid* the "eventually one candidate wins" behavior CRDT merge gives you, in favor of one requester winning **now**, before anyone starts writing. So lock state is arbitrated by `SyncServer` itself (`Room.lock`), never by racing client-side writes into shared CRDT state: Node's single-threaded event loop processes each incoming `MESSAGE_LOCK` request-response synchronously, so two "acquire" requests for the same room can never actually interleave — whichever the server happens to handle first simply wins, no merge ambiguity possible. This is also why `MESSAGE_LOCK` got a real new envelope type (see the wire protocol section above) instead of being folded into the awareness channel the way it might have been — a genuinely new concern (request/response with a real winner/loser) got a genuinely new, tiny protocol, rather than overloading one built for a different consistency model.

**`src/server/syncServer.ts` — the arbiter.** `handleLockRequest(room, ws, request)` grants an `"acquire"` if the room has no lock, the existing lease's `expiresAt` has passed, or the requester already owns it (idempotent re-acquire — this is also how a holder renews a lease before it expires, by calling acquire again). Otherwise denies with the spec's exact recommended EBUSY text (Section 3.6). `"release"` is idempotent and always acks. Two independent cleanup paths cover spec Section 2's "always TTL-based expiry, never graceful-unlock-only": the lease's own `expiresAt` (covers a hung-but-still-connected holder) and the room's `ws.on("close")` handler clearing `room.lock` if the disconnecting socket was the holder (covers the much more common case — the holder's process actually exited — without waiting out the TTL). `getLockState(docName)` is a read-only peek for tests/observability, not part of the acquire/release protocol.

**`src/client/SyncClient.ts` — `acquireLock(ownerId, leaseMs)` / `releaseLock(ownerId)`.** Each call gets a `requestId` (`` `${clientID}-${counter}` ``) and resolves via a `pendingLockRequests` map keyed by that id once the matching `MESSAGE_LOCK` response arrives — a small request/response layer on top of the same persistent WebSocket sync/awareness already use, not a second connection. If the socket closes with a request still in flight, every pending request is resolved `denied` rather than left hanging forever — a real bug caught while writing `test/lockService.test.ts`'s "drops mid-request" case, not a hypothetical.

**`src/sync/syncFileOps.ts` — `exclusivePaths`/`LockDeniedError`.** `SyncFileOps` takes an optional `exclusivePaths: string[]` (Section 7's `paths.exclusive` concept, declared here explicitly since `.agent-sync.yml`/Phase 7 doesn't exist yet — exact-path match, not globs, to keep this minimal until real config parsing exists), plus `ownerId` (defaults to a fresh `randomUUID()` per `SyncFileOps` instance — i.e. per agent/process) and `lockLeaseMs` (default 10s). `withExclusiveLock` wraps each of the three write methods: for a non-exclusive path it's a no-op passthrough (zero lock-service overhead, matching "everything else defaults to CRDT sync"); for an exclusive path it acquires **before** `consumePendingRejection` (so a lock denial never silently consumes a validation-rejection notice the agent hasn't seen yet), then releases in a `finally` — including when the write itself throws (`RangeMismatchError`, `ValidationRejectedError`, or anything else) — so a rejected write never leaves the lease held until TTL expiry over nothing. This is transaction-scoped (acquire → one write → release), not held across multiple separate tool calls; a real crash mid-write is still covered by the server's disconnect cleanup above, and the lease is a short-lived safety net for the write's own round trip, not a session-long reservation.

`LockDeniedError` (`code: "EBUSY"`) carries the server's already-spec-worded denial message plus the path appended (Section 3.6's "include concrete identifiers wherever available") — do not re-wrap the server's message in a second copy of the same "locked... wait and retry" sentence; that duplication was caught and fixed during a live smoke test (`node dist/server/index.js` + two real `SyncFileOps` instances), not by a unit test, since the unit tests only asserted the message *contained* the right substrings.

**Threaded through both interception mechanisms**, not just `SyncFileOps` directly: `McpSyncProxyOptions` and `MountOptions` (FUSE) both accept `exclusivePaths`/`ownerId`/`lockLeaseMs` and pass them straight to the `SyncFileOps` they construct internally — `SyncFsOperations`'s constructor changed from a bare `serverUrl` string to a full `SyncFileOpsOptions` object to make this possible (a real, deliberate signature break, not additive-only).

`toErrorResult`'s `.code`-based dispatch (see the Phase 5 section above on why it's `.code`, not `instanceof`, per error class) picks up `LockDeniedError` automatically on the MCP side; `mountSyncFs.ts` gained an explicit `toErrno` helper with a `LockDeniedError → Fuse.EBUSY` branch (the FUSE side still needs one branch per code, since POSIX errno constants aren't derivable from a string).

### Config + CLI + dashboard (Phase 7, spec Section 7/10)

**`src/config/agentSyncConfig.ts` — `.agent-sync.yml`.** `parseAgentSyncConfig` follows the *opposite* strictness policy from `mappingConfig.ts`'s `.agent-sync-mcp-map.yml`: every field here has a sane, spec-recommended default (the same ones `agent-sync init` writes), so an omitted field just means "use the default," never an ambiguous guess about behavior the way an unmapped MCP tool's edit mode would be — a partial, hand-edited config is fine. A *present but wrong-typed* field (`debounce_ms: "soon"`, an unrecognized `on_fail`) is still a hard parse error, same discipline as the mapping config. `validation` is the one field that's `undefined`-shaped rather than defaulted — Phase 5's `DiskFlushService` already treats "no `validation` option passed" as "no gate configured," so there's no default command to fall back to (see below for why `agent-sync init` doesn't guess one either). `writeDefaultConfig(path, force)` is what `agent-sync init` calls — refuses to overwrite an existing file unless `force`, matching `git init`/`npm init`'s usual behavior. `loadAgentSyncConfigOrDefault(path)` is the "load if present, else defaults" helper both the CLI's `server` command and any future config-consuming code should use rather than open-coding an `existsSync` check.

`DEFAULT_CONFIG_YAML` (what `init` writes) deliberately ships `validation` present but commented-out, not filled with a guessed command like `"npm test"`. Every other default here just changes this codebase's own behavior if wrong (a bad `debounce_ms` is annoying, not dangerous); `validation.command` is a shell command that would actually execute against the repo on every flush, so unlike the rest of the config it needs an explicit opt-in rather than a guessed default — the same reasoning `mappingConfig.ts` applies to ambiguous tool mappings, just for a different reason (safety of an unreviewed default action, not ambiguity of intent).

**`src/server/bootstrap.ts` — `startAgentSyncServer`.** Phase 4/5's server+flush+validation wiring (originally inline in `src/server/index.ts`) is extracted here so it has exactly one implementation shared by two entry points: `src/server/index.ts` (env-var-driven, what `npm run server` still uses — kept for backward compatibility rather than replaced, since it needs no config file to work) and the CLI's `agent-sync server` (config-file-driven). Neither entry point duplicates the "wire `DiskFlushService`, optionally in front of a `ValidationGateService`, log the relevant events" logic.

**`src/server/syncServer.ts` — `GET /status`.** The dashboard needs to ask a *running, separate-process* server "what rooms exist and who's in them" — unlike `getDocNames()`/`getDocContent()` (Phase 4), which are same-process escape hatches for `DiskFlushService`, this has to cross a process boundary. Per the wire-protocol section above, a new concern normally gets a new envelope type the way Phase 6's lock service did — but a "read-only status snapshot, polled at low frequency by a human-facing tool" isn't a CRDT/awareness concern at all and doesn't need a persistent connection, so it's a plain `GET /status` JSON response on the same HTTP server the WS upgrades already share, not a third binary message type. `getStatus()` returns `{ rooms: [{ docName, peers: [{ clientId, state }], lock }] }` by reading the same in-memory `rooms` map every other method here already uses — no new state to keep in sync.

**`src/cli/dashboardView.ts` — pure rendering, kept separate from the polling loop.** `statusUrlFor`, `describePeer`, and `formatStatus` take a `ServerStatus` (or a URL string) and return data/strings with no I/O, the same reasoning `textMerge.ts` applies to the merge algorithms — testable without a real server or a running poll loop. `describePeer` labels a peer by `state.agentId` when the caller's `setPresence()` call included one (the convention every existing test already uses, e.g. `presence.test.ts`'s `{ agentId: "agent-A", status: "editing" }`), falling back to `client-<id>` since `SyncClient.setPresence`'s state shape is caller-defined with no fixed schema — the dashboard can't assume every agent sets `agentId`.

**`src/cli/index.ts` — the `agent-sync` binary.** Hand-rolled argv parsing (no dependency added for this — three subcommands and a couple of flags each don't justify one). `init` calls `writeDefaultConfig`. `server` loads `.agent-sync.yml` via `loadAgentSyncConfigOrDefault` (falling back to defaults with a console note if the file doesn't exist, rather than refusing to start), derives the port from `config.server`'s URL, and calls `startAgentSyncServer` with `flush.debounce_ms`, `line_endings`, and `validation` — note `paths.exclusive` from the config is *not* wired into this command, because the standalone server has never taken lock options (see the Notes section below); it's consumed on the client side, by the proxy/mount/hook bridge, via `resolveSyncFileOpsOptions` (next paragraph). `dashboard` polls `GET /status` (via `fetch`, no HTTP client dependency needed) on a plain `setTimeout` loop and re-renders with `console.clear()` — no `blessed`/`ink`-style TUI framework, since spec Section 10 calls for a "basic" view.

`package.json` gained a `bin` entry (`agent-sync` → `dist/cli/index.js`, with the file's `#!/usr/bin/env node` shebang) and an `npm run cli` dev script (`tsx src/cli/index.ts`) for running it straight from source the same way `npm run server` already does for the server binary.

**`resolveSyncFileOpsOptions(config, overrides)` in `agentSyncConfig.ts` — how `paths.exclusive` actually gets consumed (Phase 7 addendum).** The one place a parsed `AgentSyncConfig` becomes `SyncFileOpsOptions`: `server` → `serverUrl`, `paths.exclusive` → `exclusivePaths`, with explicit overrides winning over the config (`exclusivePaths` *replaces* the config's list rather than merging — predictable beats clever here). A server URL from neither source throws rather than silently assuming `localhost:4600`; that default belongs to `DEFAULT_CONFIG`, and a caller that wants it passes `loadAgentSyncConfigOrDefault`'s result. `McpSyncProxyOptions` and `MountOptions` both gained `config?: AgentSyncConfig` and had their `syncServerUrl`/`serverUrl` made optional (required only without a config), then route through this resolver — so the `.agent-sync.yml` → lock-service path is one implementation, not three copies of the same field mapping. `examples/claudeCodeHook.ts` uses it too, loading the workspace's own `.agent-sync.yml` and treating `AGENT_SYNC_SERVER`/`AGENT_SYNC_EXCLUSIVE_PATHS` as overrides. A direct tool-registry rebinding integration (Section 3.3 tier 1) should call this same resolver rather than reading the config fields itself.

### Tests (`test/*.test.ts`)

Each test spins up its own `SyncServer` on port 0 and one or more `SyncClient`s connected to it, exercising real WebSocket round-trips end-to-end rather than mocking the protocol. Assertions use `vi.waitFor` to poll until state settles, rather than fixed sleeps — new tests should follow that pattern to stay robust against real network/event-loop timing. Exception: don't use `vi.waitFor` to catch a *transient* intermediate state (e.g. "awareness briefly shows nobody present mid-reconnect") when a fast, tunable backoff can make that window narrower than the polling interval — that's a flaky test waiting to happen, not a real assertion. Assert on the state before and after instead, and prove intermediate-state correctness with a scenario where it's the durable end state (see how `presence.test.ts`'s disconnect-cleanup test differs from `reconnect.test.ts`'s reconnect test).

`test/mcpProxy.test.ts` connects a real `@modelcontextprotocol/sdk` `Client` and `Server` (low-level `Server`, not `McpServer` — the proxy needs to forward an arbitrary upstream tool list, not declare its own fixed one) over `InMemoryTransport.createLinkedPair()` pairs — real MCP protocol messages, just an in-process transport instead of stdio, so a fake upstream "filesystem" server can assert mapped calls never reach its own in-memory disk while unmapped calls do.

### Claude Code hook bridge (`examples/claudeCodeHook.ts`, not core library)

An example integration for testing against real Claude Code CLI agents, not a phase deliverable. Spec Section 3.3a says a FUSE/WinFsp mount is the mechanism for CLI coding agents (no MCP layer, no rebindable tool registry in their native file-tool path) — but this repo's FUSE driver only implements enough syscalls to prove per-file merge semantics in tests (no `readdir`/`mkdir`/`rename`, so a real project's directory listing wouldn't work on the mount yet), and mounting needs macFUSE installed on the host. Section 3.3's tier 2 ("a plugin/middleware hook that runs before a built-in file tool executes") fits Claude Code too, via its own `PreToolUse`/`PostToolUse` hooks — no system install, no FUSE changes needed, fully transparent to the agent (it keeps calling `Read`/`Edit`/`Write` normally).

**How it works.** `PreToolUse` (matcher `Read|Edit|Write|Bash`) pulls the file's current CRDT-merged content and overwrites local disk with it *before* the built-in tool runs (Section 3.1's read-path-swap principle), and stashes that content in a temp-dir side-car file keyed by a hash of the doc name — a real request/response correlation problem (Post needs the exact "before" content Pre just wrote), solved with a filesystem side channel rather than shared memory, since each hook invocation is a separate short-lived process. `PostToolUse` (matcher `Edit|Write|Bash`) reads what the tool just wrote to disk and pushes it via `writeFileFromSnapshot` — the same match-or-reject discipline FUSE's `flush()` uses. A rejection (`RangeMismatchError`/EAGAIN, `LockDeniedError`/EBUSY, `ValidationRejectedError`/EVALIDATE) reverts the local file to current shared truth and exits `2`, which Claude Code surfaces to the agent as feedback — the message text already says "re-read and retry" (Section 3.6), so the agent gets a real, actionable signal instead of a silently-lost local-only edit.

**The Bash-bypass gap this uncovered.** Live-tested against a real project with two real Claude Code agents: one agent's `Edit` call was correctly rejected twice (`RangeMismatchError`/"ambiguous" — the minimized `oldStr` matched more than one location, exactly the exact-match-or-reject discipline working as intended), then the agent gave up on `Edit` and applied the same change via a Python script run through `Bash` — a tool name the hooks didn't match at all. Confirmed live: the change landed on that agent's disk but never reached the CRDT room (peeked the server's in-memory content directly; it didn't contain the change), a genuine split-brain that a later `Pre` hook on that file would silently overwrite. `extractCandidatePaths` in `claudeCodeHook.ts` closes most of the common cases: for a `Bash` call, it does a best-effort, non-shell-parsing scan of `tool_input.command` for whitespace/quote-delimited tokens that resolve to an existing file (or an extension-bearing not-yet-existing one) inside the workspace, and runs the exact same `runPre`/`runPost` per-file flow against each candidate. It is explicitly *not* a real fix — it cannot resolve a path built from a shell variable, a glob, command substitution, or a heredoc, so a sufficiently indirect Bash command still bypasses sync silently. Full coverage regardless of mechanism is what FUSE/kernel-level interception is for (it sees the actual syscalls, not the command string) — this is a narrowing, not a close.

**The seeding problem this uncovered, and its real fix.** A brand-new CRDT room used to always start empty — there was no disk→doc hydration anywhere (Phase 4's `DiskFlushService` only flushed doc→disk). Live-tested against a real scratch repo: the *first* agent to touch an already-existing file would have its `Pre` hook pull that empty room and overwrite real local content with nothing — a genuine data-loss bug. The bridge originally carried a client-side heuristic (room empty but disk isn't → seed from disk) that couldn't distinguish "never synced yet" from "someone legitimately emptied the file." That heuristic is gone: the server now hydrates a new room from its repo root's working tree on creation (`createDiskHydrator`, see the Disk flush section), so `runPre`'s read of a never-before-touched file returns the file, and the empty-vs-emptied ambiguity no longer exists — an empty room for a file that exists on disk now genuinely means someone emptied it. The consequence is a hard requirement, stated in the hook header and README: **the sync server must be started with a repo root** (`AGENT_SYNC_REPO_ROOT` or `agent-sync server --repo-root`). Against a server with no repo root, every room starts empty and the `Pre` hook will faithfully overwrite an existing local file with that emptiness. Re-verified after the change with simulated hook stdin against a real hydrating server: first-touch `Read` left local content intact, `Edit` merged and committed.

**Setup**, live-smoke-tested end-to-end (seed → two-agent edit → flush/commit → genuine conflict → correct rejection+revert), all via simulated hook stdin against a real server + git repo, no actual Claude Code process needed to prove the logic: run `git worktree add` per agent off the real project so each has its own working directory sharing one git history; start the sync server with `AGENT_SYNC_REPO_ROOT` pointed at the canonical checkout (that's what actually accumulates git commits *and* hydrates new rooms — required, see above); copy `examples/claudeCodeHookSettings.example.json` into each worktree's `.claude/settings.json` with absolute paths filled in; run `claude` normally in each worktree. The hook reads the worktree's `.agent-sync.yml` (`server`, `paths.exclusive`) through `resolveSyncFileOpsOptions`; `AGENT_SYNC_SERVER`/`AGENT_SYNC_EXCLUSIVE_PATHS` (comma-separated relative paths) are optional per-hook overrides of those two fields. Presence/dashboard visibility is necessarily spotty — each hook invocation is a short-lived process, not a persistent connection, so there's no long-lived `SyncClient` to call `setPresence` on continuously; a real "agent session daemon" would be needed for that, which is more infrastructure than this bridge's actual job (proving edits merge and conflicts get surfaced correctly).

## Notes for future phases

- `.agent-sync.yml` (Section 7 of the spec) is now read by the CLI's `agent-sync server` (`flush`, `line_endings`, `validation`, port from `server`) and, via `resolveSyncFileOpsOptions`, by `McpSyncProxy`/`mountSyncFs` (when passed a `config`) and the hook bridge (`server`, `paths.exclusive`). Still not read from it anywhere: `paths.ignore` (parsed, consumed by nothing — neither the hook's Bash path scan nor `SyncFileOps` skips ignored paths yet) and `symbol_index` (Phase 8). The standalone `src/server/index.ts` binary stays env-var-driven on purpose, and the MCP proxy's *mapping* still comes from the separate `.agent-sync-mcp-map.yml` (Section 3.2, `src/mcp/mappingConfig.ts`) — don't conflate the two files.
- Direct tool-registry rebinding (Section 3.3, tier 1 — e.g. LangChain-style `Tool(name=..., func=...)`) has no reference integration yet; when it's built, it should call into the existing `SyncFileOps`, not duplicate `McpSyncProxy`'s or `SyncFsOperations`'s logic, and should accept a `config?: AgentSyncConfig` routed through `resolveSyncFileOpsOptions` the same way `McpSyncProxyOptions`/`MountOptions` now do.
- The sync server itself still takes no lock options and never will by design — `exclusivePaths` is a client-side concept (the server stays agnostic about which paths are "hot"). `paths.exclusive` is now consumed by every `SyncFileOps` consumer that's handed a config; what's still missing is `paths.ignore`.
- Hydration reads the working tree once per room, on creation, and never again for the server's lifetime. A file changed on disk *outside* any agent (e.g. a human `git pull` in the canonical checkout) while its room already exists is not picked up — the room wins. Re-hydrating or reconciling an existing room against disk is future work; today the answer is "restart the server."
- The CLI's `dashboard` command is deliberately basic (spec Section 10: "a basic who's-editing-what view") — plain polling + `console.clear()`, no persistent connection to the server, no historical/activity log, no distinction between "editing" and "idle-but-connected" beyond whatever an agent's own `setPresence()` state happens to say. A richer dashboard is future work, not a Phase 7 gap to fix now.
- Phase 8's symbol index has no code yet. Don't start it before Phases 1–5 (now all done) are proven against real multi-agent usage, per the spec's explicit sequencing note — Phases 6/7 don't block Phase 8, but Phase 8 is still the far larger, riskier piece and shouldn't be started opportunistically alongside smaller phases.
- Phase 9 (cross-platform packaging — Node SEA/`pkg`, npm-published client SDK, install docs) hasn't been started; the `bin`/shebang setup Phase 7 added is what a real single-binary package would build on top of, not a substitute for it.
